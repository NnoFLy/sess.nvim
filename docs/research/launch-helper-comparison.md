# Research: launch-helper runtimes and private transports

## Summary

**Recommendation for human consideration, not adoption:** qualify a small compiled Linux helper, provisionally C, with a private pathname Unix stream socket. A short-lived local broker mode of the same executable can receive a bounded request over inherited pipes, hold the invoking editor's directory FD, and pass it to a tmux-side launch mode using `SCM_RIGHTS`. This avoids requiring Neovim itself to expose arbitrary ancillary messages or peer-credential APIs. Python 3 is a credible simpler-to-maintain alternative if its interpreter/stdlib dependency is explicitly acceptable; Rust is a credible alternative to C if memory-safe parsing outweighs the larger build/dependency surface.

**Still blocked:** no pairing is runtime-qualified, chosen, installed or implemented. Directory pinning can ensure execution in the originally opened directory, but an ordinary pathname recheck cannot atomically guarantee that its name stays unchanged through `execve`; the precise replacement/deletion/rename boundary needs human confirmation and adversarial qualification. A helper does not establish exactly-once launch, application readiness, crash-durable reconciliation or whole-workload termination.

## Findings

### 1. Runtime comparison and trusted dependencies

**Claim:** all three compiled languages and Python can express the required Linux operations; runtime choice changes delivery and audit costs, not the correctness obligations. **Support:** D plus explicitly labelled engineering inference. **Confidence:** high for documented mechanisms; medium for suitability; no measured size/startup/performance comparison.

| Candidate | Runtime/build trust and explicit delivery choices | Trade-off and disposition |
| --- | --- | --- |
| **Small C executable** | At runtime: helper binary, Linux facilities and, for dynamic builds, ELF loader/libc ABI. At build time: selected compiler, linker, headers and libc development files; no third-party library is inherently needed for the proposed Linux socket/FD/exec core. User may explicitly build from pinned source, install a distribution-maintained package, or accept verified per-architecture release binaries. | **Provisional simplest dependency footprint**, not a claim of safest implementation. Direct Linux APIs and a single-threaded exec path are straightforward; memory corruption, overflow, length accounting and cleanup become the project's audit responsibility. Keep parser tiny and bounded. Dynamic glibc builds need an explicit minimum ABI; static musl is another deliberate build/delivery choice, not universally portable Linux output. |
| **Rust executable** | Rust compiler/Cargo, target standard library/linker and chosen libc target at build time; explicitly enumerate any `libc`, `rustix` or `nix` crates and build scripts rather than describing them as free. Runtime need not include a Rust installation. Vendoring/locked offline builds are options, not automatic downloads. | Safe parsing/ownership reduce some C risks; Linux syscall interfaces still contain unsafe/FFI boundaries. More toolchain and dependency policy than a minimal C build. **Strong alternative** if maintainers prefer it. Static CRT defaults vary by target and require inspection, not inference from a successful build. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes), [target support](https://doc.rust-lang.org/rustc/platform-support.html), [Cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html). |
| **Go executable** | Go toolchain at build time; Go runtime is part of the executable, not a required installed interpreter. Linux syscall wrappers exist; choose frozen `syscall` APIs or explicitly approved `golang.org/x/sys/unix` dependency. Pure-Go/cgo-disabled build is plausible here; cgo builds require a C toolchain and can introduce libc linkage. | Convenient cross-building and memory-managed parsing; runtime/threading and low-level process/FD behavior need audit. Use qualified exec facilities, not an improvised post-fork Go routine. **Viable, not first choice solely for this narrow syscall shim.** No binary-size/startup benchmark supports a stronger rejection. [cgo rules](https://go.dev/cmd/cgo/), [syscall API](https://pkg.go.dev/syscall), [Exec implementation](https://go.dev/src/syscall/exec_unix.go). |
| **Python 3 script, stdlib only** | Explicit absolute CPython executable, chosen supported minor-version floor, installed standard library and extension modules/libc; helper script path/version are also trusted. No pip package is required for `os`/`socket` capabilities. User-approved system package or already installed qualified interpreter; absent/unsupported interpreter means refusal, not installation. | Most convenient inspectable source delivery, no per-architecture helper build. `os.execve` supplies argv plus replacement env, `fchdir`/FD APIs and socket ancillary messaging exist. Must handle bytes/encoding, truncation and inheritance deliberately. Interpreter/stdlib startup is a larger trust surface, not evidence of inadequate speed. **Best interpreted alternative.** Use isolated startup (`-I`, and `-S` to suppress site initialization); `-I` alone is not a blanket ban on system site customization. [os](https://docs.python.org/3/library/os.html#os.execve), [socket](https://docs.python.org/3/library/socket.html#socket.socket.recvmsg), [startup flags](https://docs.python.org/3/using/cmdline.html). |
| **Existing Neovim/Lua/libuv** | Existing qualified Neovim executable and bundled Lua/luv/libuv; a separate headless process would still be an executable dependency at the tmux spawn boundary. Need clean startup, explicit trusted script paths and no user/plugin/session script loading. | **Reuse for editor-side capture/pipe framing; not demonstrated as the complete helper.** `uv.write2` transfers supported stream/socket handles, not arbitrary directory FDs, and reviewed luv help does not expose peer credentials or `fchdir`. LuaJIT FFI could bridge these but becomes an explicit platform/ABI dependency and unsafe syscall layer, not a zero-cost reuse. A headless editor is more machinery than a small launch shim; no benchmark claim. [Pinned luv help](https://github.com/neovim/neovim/blob/779c36969e31080503be2dfccbcc3f999e289606/runtime/doc/luvref.txt), [libuv write2](https://docs.libuv.org/en/v1.x/stream.html#c.uv_write2). |

No auto-build on plugin load, curl-pipe-shell, package manager invocation, interpreter fallback or runtime download is proposed. A prebuilt option requires provenance/integrity verification, supported CPU/libc/kernel tuples, update policy and executable-path configuration. A source-build option requires deliberate user action and reviewed toolchain/dependency inputs. These are **choices for approval**, not accepted packaging. Static linkage can simplify host delivery but transfers library updates into helper rebuilds; it does not eliminate kernel/architecture constraints. No licensing comparison or license approval was performed.

### 2. Channel comparison: why a private Unix socket is plausible

**Claim:** a pathname Unix socket offers the most direct independently spawned rendezvous with peer credentials and directory-FD transfer. **Support:** D for capabilities; inference for recommendation. **Confidence:** high/medium respectively.

| Channel | Properties and costs | Assessment |
| --- | --- | --- |
| **Pathname AF_UNIX SOCK_STREAM** | Bidirectional; Linux `SO_PEERCRED`; `SCM_RIGHTS` transfers references to open file descriptions. Directory/socket permissions protect against other UIDs, subject to the host security model. Stream reads are not message frames. Filesystem name is a socket endpoint, **not a secret payload file**. | Preferred candidate. Private short per-operation namespace, explicit credentials, bounded framing and descriptor validation required. Neovim needs a qualified bridge for credentials/ancillary FDs. [unix(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/unix.7). |
| **Anonymous pipes / socketpair** | Excellent private parent-child channel; no rendezvous path. Pipe is a byte stream, capacity is finite; EOF requires all writers closed. Socketpair adds duplex and ancillary capabilities. | Preferred for **editor to its local broker**. Not by itself a route into an independently spawned child of an already-running tmux server. tmux's spawn source calls `closefrom(3)` and assigns its pane PTY; assuming arbitrary client FDs survive the server boundary is wrong. [pipe(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/pipe.7), [tmux spawn](https://github.com/tmux/tmux/blob/7f2a35ad3321f9ba57a1062ca73b1f3ff26aca53/spawn.c). |
| **Private FIFOs** | Named endpoints do not store payload like regular files; kernel buffers hold bytes. Usually need two FIFOs for request/reply, careful opening order, EOF/backpressure and permissions. No equivalent connected-peer credential/SCM_RIGHTS facility. `PIPE_BUF` atomic writes do not make arbitrary-sized requests atomic. | Plausible bytes-only alternative, inferior when directory FD transfer is needed; extra rendezvous/error cases and weaker peer identification. Not rejected as impossible. [pipe(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/pipe.7). |
| **AF_UNIX SOCK_SEQPACKET** | Ordered record boundaries plus Unix ancillary messaging; message/truncation limits still apply. | Attractive if both ends are native/Python helpers. Candidate alternative to stream, but ordinary Neovim/libuv pipes expose streams, and record sizing requires qualification. Stream is easier to integrate; not intrinsically more secure. [unix(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/unix.7). |
| **Linux abstract Unix socket** | No endpoint cleanup file, but filesystem permissions and umask do not restrict access; address remains discoverable/routable, not an authentication secret. | Viable only with explicit peer checks; unnecessary Linux-specific authentication burden versus a private pathname directory. [unix(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/unix.7). |
| **Loopback TCP; PTY/tmux send-keys; payload files/memfd** | Loopback requires separate authentication and lacks Unix FD transfer. PTY is workload I/O, not a private startup protocol. Regular payload files violate the constraint. A memfd still needs inherited/passed FD access and introduces a payload-file-like object. | No advantage here; do not adopt TCP credentials, feed secrets as terminal input, or smuggle environment through temp files, tmux buffers/options/environment, arguments or logs. A socket FD can transfer cwd without any payload file. |

**Hygiene required, not automatically supplied by AF_UNIX:** bind exclusively under an owned mode-0700 directory, use restrictive umask/socket permissions, reject symlink/type/ownership surprises, never unlink somebody else's or an ambiguous stale endpoint to make progress. Use a short generated non-secret endpoint; Linux `sun_path` is 108 bytes, so ordinary NUL-terminated pathname addressing leaves at most 107 bytes. Reject overlength instead of truncation. Cleanup must be exact-namespace-only and bounded after success/failure; timeout does not justify deleting a possibly live peer's endpoint. [unix(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/unix.7).

Validate peer UID at both sides; expected PID/process-lifetime evidence and operation binding can further prevent accidental cross-wiring. `SO_PEERCRED` reports connection-time credentials, **not** executable authenticity, Sess ownership or immunity to PID reuse. An operation ID/path is not a secret credential. Same-UID hostile code/root is outside this privacy guarantee; do not claim resistance to it. Nevertheless schema-check all inputs and never execute metadata. [unix(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/unix.7).

Require exactly the expected ancillary FD count/type; check `MSG_CTRUNC` and reject truncated/unexpected data; close every received FD on all rejection paths. Use atomic close-on-exec flags where available, including `MSG_CMSG_CLOEXEC`, and allowlist the intended PTY stdio at workload exec. Leaked writers hide EOF; leaked directory/listener/lock FDs prolong authority. [`recv(2)`](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/recv.2), [`execve(2)`](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/execve.2).

### 3. Cwd identity: pinning is necessary, but not sufficient for every wording

**Claim:** an open directory FD remains a reference across rename; `fchdir` avoids accidentally executing in a replacement pathname. It does not freeze the pathname. **Support:** D for FD semantics; interpretation/inference for policy and race analysis. **Confidence:** high for distinction, unqualified for proposed integration.

- Capture the invoking window's effective cwd before placement, including explicit API override. Opening/pinning must occur at that capture boundary, not merely when a delayed helper starts. A saved `(device,inode)` pair without a live reference is not equivalent to pinning: disappearance/reuse and mount/symlink semantics need consideration.
- Linux `O_PATH|O_DIRECTORY|O_CLOEXEC` is a plausible directory reference without requiring directory read permission; `fchdir` still checks search permission. `O_RDONLY` can wrongly exclude an execute-only directory. Decide symlink policy explicitly; `O_NOFOLLOW` alone concerns the final component, not every ancestor. Missing/not-directory/inaccessible inputs must fail, never inherit tmux's fallback cwd. [open(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/open.2), [chdir(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/chdir.2).
- **Plausible no-FFI bridge:** pinned stable luv help documents integer flags for `uv.fs_open`, `fs_fstat`, and numeric descriptor inheritance through `uv.spawn`'s `stdio`. This suggests passing the captured FD to a short-lived local helper, which can relay it via `SCM_RIGHTS`. Pinned [luv constants](https://github.com/luvit/luv/blob/f65fe9d7616f9fbcd20227fc7a73b38d1c5c180d/src/constants.c) export neither `O_PATH` nor `O_DIRECTORY`; supplying correct target-specific numeric flags requires explicit qualification. The documentation does **not** prove correct constants, inheritance/mapping or descriptor lifetime on the target tuple. Passing a decimal FD number to an unrelated tmux child is not FD transfer. [Pinned luv help](https://github.com/neovim/neovim/blob/779c36969e31080503be2dfccbcc3f999e289606/runtime/doc/luvref.txt).
- At the tmux-side boundary, receive/validate the pinned directory FD; reopen the requested absolute path and compare the referenced objects under the agreed mount/namespace policy; fail on missing/inaccessible/mismatch; `fchdir` to the original FD and check the result. Set PWD according to an explicitly agreed policy, not stale tmux state. Rechecks must not substitute the reopened replacement as cwd.
- **Replacement:** pinning prevents entry into the replacement, but would otherwise allow launch in the renamed original. Therefore pinning alone fails the human's replacement-rejection requirement. **Deletion/rename:** an open reference can outlive name removal/change; do not equate successful `fchdir` with continued pathname availability. Recheck the original requested path and reject observed disappearance or rebinding. [open(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/open.2), [rename(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/rename.2).
- **Residual TOCTOU:** path recheck, `fchdir` and `execve` are separate operations. Another actor can rename/delete/rebind after the last check, or replace and restore between observations. A directory FD guarantees the selected object, not continuous binding of a name, nor usable `getcwd` after concurrent unlink. No ordinary advisory lock binds noncooperating filesystem actors. These APIs provide no atomic “compare this path identity and exec while its binding is frozen” operation. This is researcher reasoning from the documented primitives, not an impossibility proof about every Linux isolation mechanism.

**Blocking interpretation decision:** if “reject a replaced cwd” means every replacement at any time up to actual workload execution, including transient changes, this candidate does not establish it. Do not silently reinterpret that approval as “reject replacement observed at the last check.” Human agreement on an enforceable boundary, or further mechanism research, is required. Even final permission checks cannot promise permissions will never change immediately afterward.

### 4. Payload semantics, bootstrap and resource bounds

**Claim:** the helper can bypass tmux's workload-command/environment parsers, provided only fixed helper bootstrap data enters tmux and the full request stays transient. **Support:** D for source boundaries; inference for candidate protocol. **Confidence:** medium; end-to-end secrecy remains untested.

The simplest plausible arrangement is one executable with two short-lived roles, not a daemon:

1. Editor captures command mode, exact argv/shell vector, effective cwd FD and current environment. A sanitized local-helper startup environment is separate from the workload environment. Local helper gets a bounded byte request over inherited pipe(s) and the cwd FD by qualified inheritance, then exposes a one-operation private Unix endpoint.
2. tmux starts only an absolute helper executable plus fixed mode and non-secret endpoint/operation identifiers, using a correctly qualified multi-argument tmux invocation. The tmux-side helper keeps tmux's pane PTY, connects/authenticates, receives the request and FD, checks everything, and eventually replaces itself with the intended workload. The local broker exits after bounded protocol completion/failure. No resident watcher or later phone helper is introduced.
3. Before exec, reconstruct envp exclusively from the invoking editor snapshot plus explicit overrides/unsets and the agreed backend-routing policy. Do not merge stale server variables into this payload. Keep arbitrary workload env values out of the helper's own loader/interpreter bootstrap: `LD_*`, `PYTHON*`, import paths and similar values must not gain unintended bootstrap influence. The user's intended target environment may intentionally affect its target loader/shell; that is a different trust boundary.

This is an **inference/candidate**, not an approved process topology. The bridge costs an extra short-lived process; a directly qualified Neovim syscall binding could avoid it but introduces its own dependency/ABI decision.

Important contracts:

- Mode must be explicit: omitted/nil = configured shell without command flags; explicit empty API string = shell command text of length zero; direct argv = literal nonempty vector. Empty argument strings remain valid arguments. Neovim-style Ex expansion and shell-option tokenization belong in the qualified editor-side layer, not an ad-hoc helper shell lexer. Do not send direct argv through `shell -c`. [Specify Sess term command and API behavior](https://github.com/NnoFLy/sess.nvim/issues/29#issuecomment-6384374821), [reviewed native evidence](https://github.com/NnoFLy/sess.nvim/blob/c69d831c39b18db9f96608ff948665a46659d541/docs/research/persistent-terminal-neovim-semantics.md).
- Use a versioned, data-only byte protocol with bounded lengths/counts, explicit absence/unset versus empty values, partial-read/write handling and deadlines. Do not assume UTF-8 for arbitrary Linux path/argv/env bytes; reject NUL in strings and invalid env names (`=`/NUL), duplicates or holes according to a specified policy. Never evaluate JSON/Lua/shell/tmux fragments from metadata. A length-prefixed byte encoding is a candidate, not a selected format.
- Resolve helper/interpreter/tmux executable paths explicitly from approved configuration/preflight, not stale server PATH. Define workload bare-name PATH lookup against the **final workload environment** and pinned cwd, including absent/empty PATH, relative/empty PATH entries and slash-containing names. Avoid accidentally introducing `execvp`'s ENOEXEC shell fallback where direct execution should fail. Prefer explicit resolution plus `execve`; that still leaves executable-path replacement races unless FD-based execution is separately qualified, including script/interpreter/CLOEXEC cases. [execve(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/execve.2).
- Select and document caps for total request bytes, per-string bytes, argv/env counts, fd count, buffered output, pending requests, endpoint length and deadlines. Validate before allocating and before tmux effects where feasible. Socket/pipe capacity is not an application limit. Linux combined argv/env limits depend on stack limits; each argument/environment string is limited to 32 pages on the documented modern Linux model. Include NULs/pointer overhead and handle actual `E2BIG`; do not advertise unlimited arbitrary environments or assume a universal 2 MiB allowance. No numeric product caps are selected here. [execve(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/execve.2), [pipe(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/pipe.7).
- tmux 3.8 retains argv and has command/environment logging paths; therefore neither workload argv/text nor secret values belong in the **tmux bootstrap**. Its child closes extra FDs and uses a shell for a single command argument; normal outer-shell quoting does not solve tmux parsing. Keep bootstrap tokens parser-safe and independently qualify semicolons/formats/paths. [Pinned spawn source](https://github.com/tmux/tmux/blob/7f2a35ad3321f9ba57a1062ca73b1f3ff26aca53/spawn.c), [reviewed parser negatives](https://github.com/NnoFLy/sess.nvim/blob/c69d831c39b18db9f96608ff948665a46659d541/docs/research/persistent-terminal-neovim-semantics.md).

Privacy covers transport and Sess/tmux retention: no request dump, secrets in helper argv, environment persistence, payload files, diagnostics, core dumps or traces as a convenient workaround. Disable/qualify core/logging exposure and audit crash paths. Endpoint paths/operation IDs must be non-secret. No whole-payload hash in durable metadata: even a digest can disclose low-entropy secrets. The intended workload necessarily receives its own argv/env and may intentionally print/log them; the helper cannot promise secrecy from the workload, host auditing or arbitrary target behavior. This is not authorization to weaken the stated transport guarantee.

### 5. Acknowledgement, early exit and durable uncertainty

**Claim:** request acceptance/pre-exec acknowledgement is not application readiness, and close-on-exec EOF alone cannot distinguish successful exec from helper death. **Support:** D for FD/exec semantics; interpretation for protocol outcomes. **Confidence:** high; exact native reconciliation remains blocked.

A useful candidate reports separate phases: request validated, cwd/environment prepared, authorization to attempt exec, known exec failure, observed workload identity/exit, and unknown. No “ready” label should imply application initialization. `execve` success does not return; FD_CLOEXEC closes the error channel on exec, but process crash/SIGKILL also closes it. A pre-exec message can be sent and followed by failure; a peer can die after transmitting data but before the observer persists it. A quick successful program can exit before any tmux query. These facts defeat recipes that infer launch success from tmux exit 0, EOF, timeout, an empty listing or absence of an error frame. [execve(2)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man2/execve.2), [pipe(7)](https://github.com/mkerrisk/man-pages/blob/091fbf1fef4808f0ccfe0ff8c333aedf833b8782/man7/pipe.7).

A qualified live protocol might correlate a non-secret operation ID, exact server generation/owner incarnation/window/pane/workload epoch and root process start identity. It still needs native evidence for when that relation becomes authoritative, survives quick exit, and is durably available after each crash window. An operation stamp installed after spawn is not automatically atomic with spawn; a PID or matching name/cwd is insufficient. **This report establishes none of that native identity mechanism.**

Before authorizing irreversible work, publish bounded non-secret intent under the existing locking/revision rules, using checked file and directory fsync. Persist only allowed operation/identity/status data, not a command/environment recovery recipe. Record confirmed effects afterward; failure after an effect remains an error with partial/unknown outcomes, not rollback. A lost acknowledgement after authorization means **unknown/no automatic retry** until exact evidence resolves it. Timeout is not cancellation proof and does not authorize killing a possibly running workload to simulate rollback. [Specify safe terminal persistence and reconnection](https://github.com/NnoFLy/sess.nvim/issues/30#issuecomment-6387360218), [reviewed durability limitations](https://github.com/NnoFLy/sess.nvim/blob/561ecfa8c5aa74771e6358d7aadcaf356e4668a9/docs/research/persistent-terminal-durable-recovery.md).

Do not claim exactly-once execution. At-most-one attempted execution by one cooperative helper is narrower than global exactly-once effects or durable knowledge that the workload executed. Suppress automatic replay/duplicate spawn on ambiguity. The separate approved exception remains lazy **fresh shells** with current environment after verified server loss, never replay of an old command; unknown pending operations require reconciliation/fencing rather than automatic eligibility. Verified quick natural exit must be exposed as exited, not retried. Application-specific readiness would need a separate explicit application protocol, not arbitrary shell readiness guessing.

## Contradictions and limits

- **No new contradictory primary evidence found.** Existing negative probes disprove naive recipes, not all native/helper solutions. tmux source and reviewed probes agree on cwd fallback and secret-bearing argv risk.
- “Pinned directory” and “requested pathname never replaced” are different guarantees. The latter is **not established** by pinning plus recheck. This is the principal wording/feasibility blocker, not a reason to discard the human's rejection requirement.
- C is recommended for a small dependency surface, not because documentation proves it safer or faster than Python/Rust/Go. No benchmark, implementation size, maintainer-experience survey or delivery prototype was collected.
- A source-supported bridge is not a working bridge. Existing Neovim facilities are promising for FD capture/inheritance; direct arbitrary SCM_RIGHTS/peer-credential access is not established by the reviewed public luv API.

## Missing evidence and remaining human decisions

1. Approve **runtime and delivery separately**: C versus Rust/Go/Python; interpreter version or binary ABI/CPU matrix; trusted dependency inventory; local source build versus distributor/prebuilt provenance/update policy; explicit executable paths. Nothing is installed or selected.
2. Confirm the enforceable cwd observation boundary, symlink/mount/namespace semantics, rename/removal policy and whether stricter protection requires a new scoped investigation. Continuous replacement detection must not be promised from ordinary rechecks.
3. Choose stream versus seqpacket and whether the short-lived broker is acceptable; approve binding/inheritance strategy only after target-tuple probes. Select byte encoding, caps, timeouts, PATH lookup and routing variables (`TMUX`, `TMUX_PANE`, TERM, PWD and Neovim-related variables) without silently contradicting arbitrary override/unset semantics.
4. Establish native operation-to-effect evidence and durable ambiguous-outcome/no-retry behavior before handoff. No selected runtime/channel solves that by itself. [Investigate short-lived helper feasibility for exact workload termination](https://github.com/NnoFLy/sess.nvim/issues/39) and joint attachment guards remain untouched and blocking.
